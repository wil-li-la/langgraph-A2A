# cam_bridge

Python service that pulls MJPEG from upstream `web_video_server` / Caddy,
caches the latest JPEG per camera, and re-serves to browsers as either
**MJPEG** (drop-in `<img>` compatibility) or **H.264 fragmented MP4**
(low-bandwidth `<video>`) over **HTTP/2**.

## Why this exists

- **Sidesteps the `web_video_server` wedge bug.** Each `/snapshot` request
  in `web_video_server` opens a transient ROS subscriber; under HTTP/1.1
  burst load the subscribers leak and the whole process wedges (see
  https://github.com/wil-li-la/ED305_pylon_ros/issues/1). This bridge holds
  exactly **one** long-lived `/stream` connection per camera to the
  upstream — server-to-server, no churn — and fans out to N browsers
  locally.
- **HTTP/2 origin → no per-origin connection cap.** Browsers limit HTTP/1.1
  to ~6 concurrent connections per origin. HTTP/2 multiplexes every
  camera stream over a single TCP connection, so 8 (or 16, or more) tiles
  all stay live at once.
- **Shared ffmpeg per camera.** One ffmpeg subprocess per cam, fanned out
  to N clients via per-client `asyncio.Queue`. NVENC sessions = number of
  cams, not (cams × viewers). Late joiners get the cached fMP4 init
  segment replayed before live media.
- **H.264 via `h264_nvenc`** (~10-50× lower bitrate than MJPEG) makes
  remote viewing via Cloudflare Tunnel / WAN / phone practical.

No ROS dependency — just Python 3.10+, ffmpeg, and a TLS cert.

## Setup

One-time, on the host that will run the bridge:

```bash
sudo apt install -y ffmpeg openssl
ffmpeg -encoders 2>/dev/null | grep h264_nvenc     # verify NVENC available
```

First launch — generates self-signed cert, creates venv, installs deps:

```bash
cd backend/cam_bridge
./run.sh
```

## Trust the self-signed cert (one-time, per viewer)

Browsers won't speak HTTP/2 to an untrusted cert (no interactive prompt
on `<img>`/`<video>` subresources). Trust the cert into Chrome's NSS db:

```bash
# install certutil if missing
sudo apt install -y libnss3-tools

# import the cert that run.sh just generated
certutil -d sql:$HOME/.pki/nssdb -A -t 'CT,C,C' \
         -n 'cam_bridge local' \
         -i backend/cam_bridge/cert.pem

# fully quit Chrome (close all windows), then reopen
```

For Firefox, the NSS db lives per-profile under `~/.mozilla/firefox/*/`.

## Run

```bash
./run.sh                          # uses ./config.yaml
./run.sh --config /path/to/cfg    # override
./run.sh --log-level DEBUG        # see per-frame logs + ffmpeg stderr
```

## Endpoints

| Path | Use |
|------|-----|
| `GET /` | HTML mosaic of all configured cameras (H.264 `<video>` tiles). |
| `GET /healthz` | JSON: `{ok, missing, cams: {key: {seq, age_s, bytes}}}`. `ok=true` once every configured cam has produced ≥1 frame. |
| `GET /cams` | JSON list of `{source, cams, base_url}` per source. |
| `GET /snap/<source>/<cam_id>` | Latest JPEG snapshot, instant from cache. |
| `GET /cam/<source>/<cam_id>/mjpeg` | `multipart/x-mixed-replace` MJPEG. Works with `<img src=…>`. |
| `GET /cam/<source>/<cam_id>/h264` | Fragmented MP4 H.264 from the shared transcoder. Works with `<video src=…>`. Multiple clients on the same cam share one ffmpeg + one NVENC session. |

CORS is `*` on every endpoint.

## Config

`config.yaml`:

```yaml
host: 0.0.0.0
port: 9998
framerate: 30          # JPEG fps hint to ffmpeg's mjpeg demuxer
h264_encoder: h264_nvenc
h264_bitrate: 2M

tls: true              # required by browsers for HTTP/2
cert_path: cert.pem    # generated by run.sh on first launch
key_path: key.pem

sources:
  - name: right
    base_url: https://192.168.1.13:8443     # Caddy in front of web_video_server
    insecure: true                          # skip cert verify on LAN
    cams: [3, 6, 8, 10, 12, 13, 15, 16]
  # - name: left
  #   base_url: https://<left-host>:8443
  #   insecure: true
  #   cams: [3, 6, 8, 10, 12, 13, 15, 16]
```

For **Cloudflare Tunnel** deployments, set `tls: false` and let the
tunnel terminate TLS at the edge. Plain HTTP between the tunnel client
and the bridge is fine inside the lab network — the tunnel still
delivers HTTP/2 to the browser.

## Frontend wiring

In `frontend/.env.local`:

```env
NEXT_PUBLIC_CAM_BRIDGE_URL=https://localhost:9998
NEXT_PUBLIC_PYLON_CAMS_RIGHT_URL=https://192.168.1.13:8443
# NEXT_PUBLIC_PYLON_CAMS_LEFT_URL=...
```

When `NEXT_PUBLIC_CAM_BRIDGE_URL` is set, `/cameras` renders
`<video src="…/cam/<source>/<cam_id>/h264">` per tile. When it's unset,
the page falls back to direct MJPEG `<img>` against the camera host.
`NEXT_PUBLIC_PYLON_CAMS_{RIGHT,LEFT}_URL` only drive which side is
rendered in bridge mode (the bridge has its own `config.yaml`).

## Operations

```bash
# is everything healthy?
curl -k https://localhost:9998/healthz | python3 -m json.tool

# per-camera age + size
curl -k -s https://localhost:9998/healthz | python3 -c "
import json, sys
h = json.load(sys.stdin)
for k, v in sorted(h['cams'].items()):
    print(k, 'age', v['age_s'], 's', 'seq', v['seq'], 'bytes', v['bytes'])"

# confirm HTTP/2 is actually negotiated
curl -k -sI https://localhost:9998/ | head -1     # expect: HTTP/2 200

# how many NVENC sessions / fps right now
nvidia-smi --query-gpu=encoder.stats.sessionCount,encoder.stats.averageFps \
           --format=csv
```

When the upstream `web_video_server` wedges (issue #1 on the camera-host
repo), the bridge's pullers sit in exponential-backoff loops and
`/healthz` shows stale `age_s`. Recovery is a `systemctl restart
pylon-cameras` on the camera host — the bridge auto-reconnects.

## H.264 latency / quality knobs

| Setting | Effect |
|---|---|
| `h264_bitrate: 2M` | ~2 Mbps per stream. Bump for sharper text/edges; drop for tunnel use. |
| `framerate: 30` | Pass-through fps hint. Real cap is camera publish rate (~30-50 Hz). |
| `-g 30` (in ffmpeg cmd) | Keyframe every 1 s. Lower = faster recovery, larger output. |
| `-frag_duration 100000` | 100 ms fragments. `<video>` decode latency ≈ fragment + one-frame buffer. |

NVENC concurrent-session caps on consumer GPUs:
- Older Pascal/Turing: 3 sessions
- Ampere: 5 sessions
- Ada Lovelace (4080 SUPER): effectively unlimited on driver 530+
With the shared-transcoder pool, sessions = number of distinct cameras
streamed by any client. For 16 cams long-term, this stays within all
recent drivers' caps.

## Why not WebRTC?

Sub-100 ms latency would be nice, but WebRTC adds ICE / SDP / signaling
plumbing that's overkill for a monitoring panel. Fragmented MP4 over
HTTP/2 gets us ~500 ms end-to-end on LAN with zero JavaScript on the
frontend (`<video src="…">` just works).
